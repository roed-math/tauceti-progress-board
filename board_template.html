What exists today, and why this page is missing

Three things already report on Tau Ceti, and none of them answers "how far along is each roadmap".

  • The Statistics page on the TauCeti site plots lines of Lean per roadmap over time (stacked, from the roadmap/<Area> labels), the pull-request pipeline, and contributors. It measures volume and throughput, not distance to the specification.
  • STATUS.md is a per-roadmap prose snapshot written by TauCetiProgress. Its "Roadmap coverage" paragraph is exactly the per-layer judgment this board needs, but it is prose, so nothing can aggregate it, and of roadmaps have one.
  • The roadmap repository's README.md lists the roadmaps with no state at all.

So the missing piece is small: a machine-readable per-layer verdict beside the prose, and a page that reads it together with the label data the site already collects.

The design

1. One row per roadmap, one segment per layer

The unit of progress is the layer (or lane, part, stage) as the roadmap's own README.md names it. That is the structure the STATUS prompt already tells the writer to follow, it is what humans wrote, and it does not change when code lands. Each segment carries one of four states: done, partial, untouched, unassessed. Percentages are deliberately absent. Layers are not equal in size, and a false-precision "62 %" invites the wrong comparison; a strip that is mostly solid reads correctly at a glance.

2. Three classes of evidence, kept visibly apart

ColumnSourceTrust
Layers, coveragea tauceti-coverage:v1 marker in STATUS.md, written by the same run that writes the prosemodel-judged, same standing as the prose: not security-validated
Merged PRs, last mergedroadmap/<Area> labels on merged TauCeti pull requests, exactly as the Statistics page uses themmechanical
Completedthe roadmap sits under Completed/; its Suggested.lean targets are closed by Tau Ceti declarations and elaboratedkernel-checked

The column headers say which class each column is, and the row detail repeats it. A reader should never mistake a model's reading of the library for a proof that a layer is done.

3. The one change TauCetiProgress needs

The status writer is given the README, so its script can extract the layer headings (every heading matching Layer|Lane|Part|Stage) before the model runs, and hand the model a fixed list of layer ids. The prompt then asks for one extra fenced block after the prose, one line per id, state from the four words above. The script validates that every id is present exactly once with a legal state, rejects anything else (as it already rejects stray tauceti-* markers), and writes the result into the file head:

<!--tauceti-status:v1 {"roadmap":"EllipticCurves","to_sha":"f5c212c…","ts":"2026-08-30T22:49:04Z"}-->
<!--tauceti-coverage:v1 {"roadmap":"EllipticCurves","to_sha":"f5c212c…","layers":[
  {"id":"Layer 0","state":"partial"}, {"id":"Layer 0.5","state":"partial"},
  {"id":"Layer 1","state":"partial"}, {"id":"Layer 2","state":"untouched"}, …,
  {"id":"Layer 6","state":"partial"}, {"id":"Layer 7","state":"untouched"}]}-->

The merge gate in TauCetiProgress already proves the paths and the markers of a generated update; the new marker is one more shape check. Nothing about the trust boundary changes: the verdicts are the prose's verdicts, made countable.

Three roadmaps need a nudge so the extractor finds their layers: ConformalMapping names its layers in a bullet list rather than headings, and CFSGStatement and HodgeStructures have no layer headings at all (this prototype hand-lists their lanes from the README and STATUS prose). A one-line rule in the roadmap-writing checklist ("name every milestone in a ### heading starting Layer, Lane, Part or Stage") settles it for future roadmaps.

4. Where the page lives

On the TauCeti site, as a Progress page beside Statistics. The Pages workflow already clones TauCetiRoadmap and reads labels through gh every three hours, so a scripts/roadmap_progress.py next to loc_roadmap_graph.py can emit progress.json plus the rendered board into web/static_files/ with no new permissions and no committed state. The JSON is the durable product; the board is one rendering of it, and the roadmap repository's README could carry a one-line badge per roadmap from the same file.

5. Summary before detail

The four tiles answer the project-level question first: how many roadmaps, how many layers in each state across the assessed ones, how much merged in the last month, how fresh the snapshots are. Sorting by activity puts the live roadmaps at the top; sorting by coverage answers "what is nearly done"; sorting by update due is the maintainers' to-do list for the reporting run; sorting by topic groups the roadmaps into six mathematical areas, a hand assignment that a topic: line in each README could replace. An "update due" chip marks a roadmap with ten or more pull requests merged since its snapshot, which is the threshold TauCetiProgress itself uses to open a new window; a snapshot is always somewhat behind, so plain age is not the signal.

What this prototype fudges

The coverage marker does not exist yet, so every strip above was read by hand from the STATUS prose. Where the prose names a layer's state plainly the segment is solid; where it only implies one, or says nothing, the segment is hatched. The eleven representation-theory sub-roadmaps are the worst case: one paragraph covers all eleven, so most of their layers are hatched, and their activity cannot be split because they share a single roadmap/RepresentationTheory label. That is the argument for the marker in one picture.

Merged-PR counts include every pull request carrying exactly one roadmap label, maintenance included; the Statistics page excludes maintenance from its line counts, and the real build should pick one rule and say so.
